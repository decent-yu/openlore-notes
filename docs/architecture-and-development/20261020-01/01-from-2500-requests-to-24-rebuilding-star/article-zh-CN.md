### [Taylor Cuilty](https://github.blog/author/taylorcuilty/)

高级软件工程师

我们新的仓库星标历史 API 现在可以提供趋势数据，无需返回个人身份信息，也无需让数据库执行工作量无上限的操作。以下是我们所做的工程权衡。

维护者查看星标历史，是为了回答一个实际问题：一次上线、版本发布或活动，是否改变了项目的发展轨迹？为了通过 GitHub API 重建这条曲线，工具过去必须逐页请求星标用户记录（即当前为仓库添加星标的每个人，以及他们添加星标的时间），保留时间戳，再丢弃身份信息。

随着时间推移，这种设计在两方面都带来了问题。身份信息可以被批量收集，于是不法分子开始抓取公开的星标用户列表，用于发送垃圾信息和开展网络钓鱼。对于星标数量很多的仓库，这个端点还可能让数据库处理数以万计的条目，仅仅为了返回一页结果。

解决办法似乎很明确：返回计数，而不是用户。但返回的数据更少，并没有真正降低查询成本。

现在，维护者有了直接获取这条曲线的方法：我们构建了一个端点，一次请求最多返回 30 周的每日星标数，不附带任何身份信息。要以较低成本提供这项服务，就必须减少数据库处理的数据量，而不只是减少返回的数据量。这个端点通过**先按时间筛选星标，再进行任何计数**来做到这一点。

我们首先通过[将星标用户和关注者列表的访问权限限制为仓库管理员及协作者](https://github.blog/changelog/2026-06-30-upcoming-access-restrictions-to-public-api-endpoints-and-ui-views/)，应对开发者和数据库面临的迫切风险。访问权限变更后，不具备所需权限的调用者可能会收到空响应或 `403 Forbidden` 响应。

这项变更也阻断了一些工具：它们原本使用旧响应来计算星标历史，通常并不展示或以其他方式使用响应中返回的用户名。因此，我们与维护者和工具开发者进行了交流，以了解他们仍然需要什么。他们将星标历史视为衡量关注度的近似信号：比较版本发布前后的活跃情况，或查看一则公告是否触达了新的开发者。他们关心的是那条曲线。

旧 API 响应让身份信息看起来像是接口约定的一部分，因为每个时间戳都附带一个用户。实际上，Star History 等工具需要的是计数和日期，而不是用户名或其他用户数据。一旦身份信息不再属于需求的一部分，我们就可以围绕实际任务设计一个聚合端点：以有用的时间粒度，获取星标数量随时间的变化。

当 API 变更影响到 Star History 时，用户纷纷支持这个项目。GitHub 社区团队倾听了大家的声音，并帮我们联系了产品工程团队。后者深入了解了我们的使用场景，与我们共同设计了一个专用端点。一次困境变成了 GitHub、Star History 和更广泛社区之间富有成效的合作，最终带来了更好的解决方案。

Tianzhou Chen，star-history.com 维护者兼 Bytebase 联合创始人

明确维护者的需求后，下一步就是弄清楚原有设计为什么无法以较低成本满足这些需求。最初的 `GET /repos/{owner}/{repo}/stargazers` 端点旨在回答一个简单问题：谁为这个仓库添加了星标？它返回一个分页的用户列表，如果请求指定了自定义媒体类型，每个条目还会包含星标的创建时间。

星标模型也是为同样的任务构建的。它记录当前为仓库添加了星标的用户集合，让显示星标数量或星标用户列表都很简单。它并非按历史事件日志来设计：当有人取消星标时，对应记录就会被删除。当工具开始将这个列表用作时间序列时，重建增长曲线就意味着必须获取个人身份信息，并处理当前的每一个星标。由于每页最多容纳 100 人，工作量会随着仓库热度上升而增长：对于约有 251,000 个星标的 `react/react`，构建完整曲线需要约 2,511 次请求，因此工具经常触及速率限制，或选择抽样读取部分页面，而不是读取全部页面。

返回一页结果需要数据库查询该仓库当前的星标。由于分页实现存在一个缺陷，每次请求还会统计所有这些星标，以计算共有多少页，尽管调用者只能收到一页、最多 100 人的结果。对于星标数量很多的仓库，这意味着每次请求都要对数以万计的条目进行计数。在我们限制访问前的一周内，近 37,000 次此类计数查询因运行缓慢而被记录下来，平均每次耗时接近 3 秒，其中超过 1,000 次被数据库保护机制终止，这也是造成请求超时的原因之一。

下图展示了这些计数操作的成本。在我们限制访问后，数据库处理的星标用户请求减少了约 60%，花在计数查询上的总时间减少了约 80%。

移除身份信息满足了隐私要求。更难的部分是避免每次请求都扫描仓库当前的全部星标。

我们的首次技术验证仍然为每个星标保留一条记录，并向没有协作者访问权限的调用者返回 `starred_at` 值，但不返回星标用户的身份信息。起初，这看起来是推进工作的最快途径，因为它直接满足了工具开发者向我们提出的需求。只需对现有序列化和授权流程做相对较小的改动，也能阻断身份信息的批量采集途径。

这种方法解决了身份信息暴露的问题，也能让现有工具继续运行。但 API 使用方仍需逐页读取并处理可能多达数万条的单独记录，才能构建聚合后的历史数据。它还将新的使用场景绑定到了一个为列出用户而非获取趋势设计的端点及分页模型上。

聚合似乎是显而易见的下一步。查询可以不再为每个星标返回一行，而是将星标按天或周分桶，对这些桶排序，再对规模小得多的结果进行分页。

问题在于分页发生的位置。在直接编写的 SQL 查询中，数据库会先找到该仓库的所有星标，将它们分组到各个桶中，再对这些桶排序。只有在这之后，它才会应用控制返回多少个桶的 `LIMIT`，以及决定页面起始位置的 `OFFSET`：

`all matching stars -> bucket every row by day or week -> sort every bucket -> OFFSET/LIMIT -> response`
对于热门仓库，一次匿名请求仍可能扫描并聚合数以万计的索引条目，仅仅为了返回少量桶。返回更少的桶会缩小 JSON 响应，但无法减少数据库此前已经执行的高成本分组和排序操作。对于 `react/react`，用这种方式读取完整历史将意味着检查大约 600 万行，因为 24 次请求中的每一次都会重新处理它的全部星标。要降低查询成本，我们必须在开始聚合之前缩小行的范围。

我们最终上线的设计按日历周对星标历史进行分页。对于每次请求，它都会将 `page` 和 `per_page` 转换为一个有索引支持的 `created_at` 范围，将星标筛选到这些周内，然后将匹配的记录分组，得到每日计数。一次响应最多包含 30 周，增大 `page` 会向前追溯仓库的历史。

`indexed date range -> group rows in that range -> daily buckets -> response`
先应用日期范围后，每次请求处理的就是要返回的那些周，而不是仓库当前的每一个星标。对工具而言，这意味着无论仓库有多少星标，一次请求现在都能覆盖最多 30 周的历史。对于 `react/react`，这大约只需 24 次请求，而原来约需 2,511 次；在读取完整历史的过程中，数据库对每个星标大约只检查一次（总计约 251,000 行）。这符合主要使用场景，因为维护者通常会查看数周内的增长情况，或围绕一次已知的版本发布、上线或活动进行查看。按周划分的范围也与其他仓库活动 API 一致：响应采用与[每周提交活动端点](https://docs.github.com/rest/metrics/statistics#get-the-weekly-commit-activity) `GET /repos/{owner}/{repo}/stats/commit_activity` 相同的结构。

时间范围设计将每次请求限制在一个明确的时间段内，但不会限制该范围内的星标数量。因此，如果某一周的星标数量异常庞大，仍可能产生缓慢或成本高昂的查询。常规请求流程不再查询当前的每一个星标，但星标异常密集的周仍然是扩展能力的一项限制。

对比新旧 API 路径的性能时，我们还发现了 GitHub 其他按需统计星标数量的地方。我们在 GitHub.com 的仓库星标用户页面上发现了同样的模式，并将其改为使用仓库缓存的星标数量。该页面原本每周有数百次慢查询，改动后降到了零。我们最近也为其他星标用户 API 端点上线了类似修复。

`LIMIT` 和 `OFFSET` 减少了返回的结果数量，但没有减少数据库此前已经完成的分组和排序工作。我们必须审视这些工作的执行顺序。
限制原端点的访问解决了眼前的问题。倾听维护者的需求，让我们得到了比最初方案**更好**的结果：星标历史更容易获取，提供服务的成本更低，对每一个给项目添加星标的人也更安全。
