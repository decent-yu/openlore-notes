## 原文整理

# Origin Range Requests：无需调整范围请求参数，即可高效传输大文件

![](assets/diagram-a38abfb9b2d5.webp)

视频播放器跳转到电影中间时，只会请求几兆字节的数据。但在我们旧的范围缓存机制下，仅这一个请求，就可能让 Cloudflare 从源站拉取 128 MiB 的数据，并在数据中心之间传输，有时甚至在观众已经离开后仍在继续。范围请求是大文件传输的重要方式；而大规模运营 CDN 时，如果缓存方式过于简单，就很容易浪费网络带宽和磁盘操作。

因此，我们重新实现了缓存处理范围请求的方式。对于 Cloudflare 的对象存储服务 R2，首字节时间的第 99 百分位（p99）下降了约一半；随后的一项改进，又使 R2 及类似工作负载的[分层缓存](https://developers.cloudflare.com/cache/how-to/tiered-cache/)流量减少了约 6%。

今天，我们以 [Origin Range Requests](https://developers.cloudflare.com/cache/how-to/cache-rules/settings/#origin-range-requests) 的形式，向所有套餐开放这套新实现，用户可以自行启用。无需调整范围大小，也无需联系支持团队。通过一条[缓存规则](https://developers.cloudflare.com/cache/how-to/cache-rules/)开启它，剩下的交给 Cloudflare。

## 请求文件的一部分

HTTP 范围请求用于请求资源的一部分，而非整个资源。客户端发送普通的 `GET` 请求，并附带 `Range` 标头：

```
GET /movie.mp4 HTTP/1.1
Host: example.com
Range: bytes=1048576-2097151
```

如果服务器支持这一请求，就会返回 `206 Partial Content`，并用 `Content-Range` 标明所返回的字节范围：

```
HTTP/1.1 206 Partial Content
Content-Range: bytes 1048576-2097151/524288000
Content-Length: 1048576
```

范围请求常用于大型对象。视频播放器可以请求跳转位置附近的字节，而不必请求整个文件。下载管理器可以在下载中断后续传。包管理器可以获取构建产物的一部分。客户端也可以查看文件末尾，而不必先下载前面的所有内容。

是否请求某个范围，由客户端决定，Cloudflare 不会更改这个请求。Origin Range Requests 改变的是 Cloudflare 满足请求的方式。

## 范围大小带来的问题

多年来，Cloudflare 一直通过站点级静态配置支持范围请求缓存。

之前的实现类似于[一篇 nginx 博客文章](https://blog.nginx.org/blog/smart-efficient-byte-range-caching-nginx)中描述的缓存切片：每个客户端请求都会映射到文件中大小固定的若干范围，范围大小和适用的文件扩展名按站点配置。

范围大小需要权衡。范围较小时，会产生大量小型回源请求；Cloudflare 需要在内存中合并处理这些请求，因此也会承受内存压力。范围较大时，Cloudflare 下载的数据又会远超客户端所需。更改范围大小还会使缓存条目失效，因为范围大小本身就是缓存键的一部分。

这种设计也会让通过我们网络访问这些文件的用户遇到糟糕的体验。只要并发请求落在同一个固定范围内，无论各个客户端实际请求的字节范围相距多远，都可能相互阻塞。我们基于 nginx 的缓存也无法同时使用范围缓存和[并发流式传输](https://blog.cloudflare.com/introducing-concurrent-streaming-acceleration/)。后者是我们开发的一项功能，允许多个客户端在文件仍被写入缓存时就开始从缓存读取。两者同时开启会导致响应提前中断，因此，每个范围都必须完整下载后才能供人读取；即使文件很热门，每个范围仍需要单独回源获取。

这些多余的字节还可能经过分布式缓存的多个环节：先从源站传到一个数据中心，再在缓存层级之间传输，最后向客户端传送。每多经过一跳，浪费就多一份。无论是只跳转读取一小段、按顺序下载、传输大型媒体文件，还是面对不同的源站和缓存拓扑，都不存在一个同样适用的范围大小。

我们内部缓存的局限，就这样直接暴露给了客户。而客户本不该为了高效传输文件，就必须深入了解我们的系统能力。

好在我们从 nginx 迁移到基于 [Pingora](https://blog.cloudflare.com/how-we-built-pingora-the-proxy-that-connects-cloudflare-to-the-internet/) 的缓存服务器，这给了我们解决这些实现问题的机会。正是这些问题，才迫使我们把一项难用的设置交给客户。

## 固定大小的缓存块

解决办法来自 Pingora 已经在做的一件事。为了方便恢复中断的下载，它会将每个缓存文件按固定大小分块存储在磁盘上。既然缓存本来就按块工作，范围大小完全不必再成为一项设置，直接使用块大小就可以了！

收到范围请求后，Cloudflare 会检查所请求的字节中哪些已经缓存，并直接返回这些字节。对于缺失的字节，它会向源站请求与缓存块边界对齐的范围，将结果存入普通缓存存储所使用的同类块中，并且只向客户端返回其请求的字节。

例如，请求字节 `150-250` 时，Cloudflare 可能会获取包含这些字节、且边界对齐的整个块。但下游响应仍然只包含 `150-250`。

对于小于缓存块的请求，这并不能消除额外工作：这样的请求仍可能需要获取它所在的整个块。对于未与块边界对齐的范围，我们也要承担额外工作的成本。区别在于，这些额外工作有明确的上限，也可以预估，不再取决于客户选择的范围大小，避免了这种设置给我们和源站带来难以预料的影响。

## 协调缓存数据和下载中的数据

解析 `Range` 标头并不难。更难的是，当所请求的字节分散在已缓存的数据、源站响应和正在进行的下载中时，如何生成一个正确的响应。

概括来说，边缘节点会：

1. 查找资源的标头，以及记录已缓存范围的元数据。
2. 尽可能从磁盘或内存中正在流式传输的数据里读取所需内容。
3. 使用边界对齐的范围请求，从源站获取缺失部分。
4. 写入新获取的字节，并在元数据中记录已完成的范围。
5. 合并各部分数据，为客户端响应设置 `Content-Range` 和 `Content-Length`。

![](assets/diagram-c2f8a700c02d.webp)

这需要一套协调机制，而不是一次简单的缓存查找。一个请求可以先使用已缓存的前段，再接上正在下载的部分，最后使用新获取的尾段。内部收到的源站响应可以大于下游响应，但下游响应的状态码和标头只描述客户端请求的范围。

如果已有下载涵盖了另一个请求所需的字节，后一个请求就可以接入这次下载，无需再次回源获取。这样，当热门大文件的请求量突增时，多个请求就能共享同一次下载。

这一设计沿用了现有的缓存数据模型。标头标识资源版本，响应体分成大小有上限的块存储，元数据则记录哪些范围已成功写入。

## 先验证，再组合

只有当所有字节都属于同一种资源表示时，组合出的范围响应才是有效的。协调机制会检查每个源站响应是否与请求的范围一致、资源总大小是否保持不变，以及各个子请求的实体标签是否一致。

`If-Range` 标头让客户端可以附带条件来请求某个范围：只有资源表示仍与已知的验证标识匹配时，才返回该范围。如果不匹配，Cloudflare 就会返回完整的资源表示，避免将不同版本的字节组合在一起。

对于即将解压的资源表示，Cloudflare 也不会组合范围，因为在压缩字节上选取的范围，与在解压后的响应中选取同一范围，得到的内容并不相同。在这些情况下，Cloudflare 会返回经过转换的完整响应，而不会声称返回了一个它无法正确提供的范围。

最终行为遵循标准 HTTP 语义：

- 对于能够满足的范围请求，返回 `206 Partial Content`，并附带准确的 `Content-Range`。
- 对于无法满足的范围请求，返回 `416 Range Not Satisfiable`。
- 对于无法安全地按范围返回的响应，返回完整的资源表示。

## 生产环境中的变化

在向所有用户开放 Origin Range Requests 之前，我们先将旧范围缓存功能的现有用户迁移到新实现，首先迁移的是给我们造成最大困扰的工作负载。

这些工作负载会针对非常大的文件发起大量并发范围请求，而且流量往往会剧烈突增。旧系统中配置的范围大小，从几十千字节到几十吉字节不等。范围较大时，一个请求所需的数据连一张软盘都装不满，却可能让我们从源站下载相当于几张 DVD 的数据，再在多个数据中心之间传输，有时客户端早已放弃，转去别处了，这些传输却仍在继续。范围较小时，一个请求又会变成一长串细小的回源请求，每个请求在等待期间都要占用内存。这两种模式都曾给我们造成实际的运维事故。

R2 是内部最大的使用方。它配置的范围大小为 64 MiB，因此，一次跨越范围边界的小规模读取，就可能带来 128 MiB 的数据中心间传输。将 R2 迁移到新实现后，我们观察到：

- **响应更快。** 在 R2 的各个存储区域，无论缓存命中还是未命中，首字节时间的 p99 都下降了大约一半。
- **网络中传输的字节更少。** 最近的一次改进，让协调机制可以在同一个响应中组合磁盘上已有的字节和从上游获取的字节。此前，一个请求要么全部由缓存提供，要么全部从上游获取。在为 R2 启用这一改进后，R2 及类似工作负载的分层缓存流量周环比下降了约 6%，相当于数据中心之间每天少传输了数 PB 的数据。

## 开始使用

缓存不再依赖客户选择范围大小后，产品配置也就变得再简单不过。客户通过[缓存规则](https://developers.cloudflare.com/cache/how-to/cache-rules/)选择要匹配的流量，Cloudflare 负责分块和缓存协调。

Origin Range Requests 适用于客户端通常只会请求大型可缓存对象中一部分内容的流量：

- MP4 等可边下载边播放、支持跳转播放的视频
- 支持断点续传的大文件下载
- 软件分发和软件包仓库
- 磁盘镜像、归档文件及其他大小为数 GB 的对象
- 需要传输大型模型文件，或获取模型产物中特定区域的 AI 训练和推理工作负载
- 获取大文件中元数据或一小部分内容的客户端

我们计划将其设为网络上某些文件类型的默认传输方式，并允许通过缓存规则修改。

这项功能不会改变通常的缓存资格规则。开启它，并不会让原本不可缓存的响应变得可以缓存。源站也需要支持字节范围请求，按范围回源获取才有实际作用。

要开启它，请创建一条匹配大文件流量的[缓存规则](https://developers.cloudflare.com/cache/how-to/cache-rules/)，并将 Origin Range Requests 设置为 On。你可以在控制台的 Caching > Cache Rules（缓存 > 缓存规则）中操作，也可以通过 API 设置 `origin_range_requests: { "mode": "on" }`。客户选择适用的流量，边缘节点负责协调缓存并确保响应正确。
