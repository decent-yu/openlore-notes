每天，数百万开发者在 GitHub 上构建客户赖以开展业务的产品、参与开源项目，并推进自己的个人项目。多年来，GitHub 的架构一直在持续演进，以支持这些工作，并满足依赖 GitHub 的开发者和组织不断增长的需求。

这就是为什么快速克隆只能解决一部分问题。读取相对容易扩展：增加缓存、增加副本，就可以向更多客户端提供相同的字节数据。扩展读取能力必不可少，但这些工作负载需要的不止于此。写入要难得多。每次推送都必须先得到持久保存，并以一致的方式对外可见，下一个智能体或 CI 作业才能在此基础上继续工作。

现有架构多年来一直很好地服务着开发者。每个仓库都由 [Spokes](https://github.blog/engineering/infrastructure/stretching-spokes/) 存储，它会在多台文件服务器的本地磁盘上保留完整副本，默认是五份。高速本地磁盘让 Git 操作能够以低延迟读取原生仓库数据；额外的副本既提供了冗余，也将读取请求分散到多台文件服务器上。当一次推送更新引用时，三阶段提交协议会通过法定数量的副本，确保 CI、网页界面和 API 客户端看到一致的仓库状态。如今，这套组合支撑着 10 亿个仓库。

然而，我们用于保证数据持久性的机制，也是我们用于扩展容量的机制。磁盘上的副本是权威数据源，因此，增加读取能力就意味着再增加一个持久副本。每个副本都参与每次写入，所以一次推送的速度取决于这组副本中最慢的那个。最终结果是：为了分担读取负载而增加副本，会让写入变慢。

对大多数仓库来说，这种权衡行之有效。但当活动量达到最高水平时，它就成了瓶颈：增加读取副本会增加写入开销，失去一个副本会削弱读取能力，而一旦可用副本不足法定数量，写入就会完全停止。要满足以智能体为核心的开发需求，我们需要将持久性保障与容量扩展分开，同时保留团队如今赖以开展工作的能力。

我们正在保持 GitHub 正常运行的同时重建基础设施。我们没有一个能让全世界的代码停止流动的维护窗口，也绝不会要求人们为了配合这项工作而改变软件开发方式。

我们面向的是 GitHub 上要求最苛刻的工作负载：必须遵守严格监管要求才能发布软件的企业、在用于构建操作系统的仓库中合入一项改动的团队，以及让数千个智能体在同一套代码上工作的组织。为这样的规模进行工程设计，也能提升所有用户所享有的基础能力。无论是审核来自不同时区志愿者贡献的维护者，还是首次发起拉取请求的学生，都能获得同样更快、更具韧性的基础设施。

新架构还必须保留团队已经在使用的管控机制。维护者需要分支保护和强制审核，确保未经审核的改动绝不会进入默认分支。安全团队需要审计日志和仓库可见性，以调查可疑的访问事件。值班工程师需要可靠的自动化，以及足够的可观测性，才能弄清部署失败的原因。

我们正在构建一种扩展能力大幅提升的 GitHub 新架构。我们的方法以分布式系统设计的核心原则为中心，将这些原则应用于智能体软件开发的并发需求和规模。我们的目标是，让世界各地使用 Git 和 GitHub 构建项目的开源社区和企业继续向前发展，同时保留并调整围绕它们建立的功能和管控机制，以满足智能体时代的新需求。

接收大量推送的仓库必须能够快速接收并发布更新。当协调用于保障正确性时，它很有价值；但过多的协调会限制写入吞吐量，让繁忙的仓库成为瓶颈。我们当前的架构在一些本无必要的地方耦合得过于紧密，导致我们在扩展读写能力时，不得不做出艰难的取舍。我们正在重新设计系统，保留 Git 语义所必需的协调，让其他工作都能独立推进。

如今，本地磁盘上的完整仓库副本既承担持久化存储的职责，也负责响应 Git 请求。将两者分离，就能让我们分别独立扩展它们。

这些原则共同作用，让我们既能支持更高的吞吐量和更多并发工作，也能保留用户所需的可靠性和管控能力。
