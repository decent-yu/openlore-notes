## AI 导读

GitHub 迁移 Git 仓库时遇到一个问题：旧系统在每次写入期间锁住整个仓库，并等待所有健康副本响应或超时，因此跨地域约 25 毫秒的一次网络往返会拖慢整个仓库的写入队列，繁忙仓库尤其难以承受。文章提出将串行执行范围缩小到单个 Git 引用，即分支、标签等指向提交的名称；修改同一引用的写入仍需排队，修改不同引用的写入则可并行。作者报告，在模拟真实流量的内部测试中，不同引用的写入吞吐量提高了 3—4 倍，延迟也有所下降。这种收益依赖写入分散到多个引用，每次写入本身仍需承担跨地域延迟。

接着，系统通过一个不保留持久本地状态的“虚拟写副本”将数据写入 Azure Blob Storage 对象存储，并把对象存储持久化纳入写入确认条件。它还能合并不同引用的并发写入，摊薄网络往返开销。在此基础上，虚拟读副本可从对象存储加载缓存，无需加入协调写入的副本组，从而按读取需求独立扩容，并为读写使用不同的资源配置。

文章展示了逐步迁移和扩容的路径，但这些能力处于不同推进阶段，不能把内部测试结果视为全面上线后的效果。读取测试先触及压测工具上限，未给出可量化的容量结论；测试配置、故障处理和读副本一致性机制也未充分说明。写入仍需等待保存完整仓库的副本，更进一步的写入扩展方案留待后续介绍。

我们已将 GitHub 上 99.99999% 的仓库各迁移了一份副本到 Azure。下面将介绍，按引用划分的仲裁组将如何帮助我们迁移剩余仓库，以及对象存储如何让读取能力独立扩展。

过去一年，Git 流量呈指数级增长，与此同时，GitHub 上 99.99999% 的 Git 仓库开始同时存在于两个地方：我们自己的数据中心和 Azure。剩下的仓库属于平台上最繁忙的一批，而阻碍它们迁移的只有一件事：一次耗时 25ms 的网络往返。

本文将介绍连接新旧设计的近期过渡方案。我们会讨论，如何改变仲裁组对写入操作进行串行处理的方式，让最繁忙的仓库也能迁入 Azure，以及这一步如何让副本无需再保留自身的持久状态。

这次迁移的时间安排和实施方式，是由向智能体开发的转变所决定的：流量迅速增长，我们的数据中心及周边地区的供电能力存在硬性上限，实体设备的供应链也受到限制。迁移开始时，即便把所有可能的扩容都算上，剩余容量也只够让我们安全地完成迁移，没有余裕慢慢来。

虽然我们已经为在云基础设施上扩展 Git 的新架构方案制作了原型，但在如此快速的增长下，同时更换存储架构和托管平台，风险实在太高。考虑到我们的规模，以及这项服务对社区的重要性，我们必须谨慎安排工作顺序：先迁移数据，等数据迁移到位后，再逐步演进架构。

Git 操作属于 Tier 0 服务：它是 GitHub 的核心功能，而 GitHub 几乎所有功能都依赖仓库数据。这意味着，数据、服务及其每一项依赖都必须先迁过去。2025 年 8 月，第一个仓库副本落地 Azure 的美国中部区域。如今，大多数仓库的五个副本中已有两个位于 Azure，约一半的 Git 流量由 Azure 承接。在这段时间的大部分时候，我们自有数据中心的规模保持稳定，新增负载则由 Azure 承接。

迁移过程中，流量会随数据一起转移。大多数仓库都有五个副本，以平衡数据持久性、可用性和扩展能力。为了尽量降低读取延迟，Spokes 会优先将请求路由到与请求位于同一区域、同一可用区的副本。随着副本迁入 Azure，每迁入一个，Azure 能够承接的流量占比就会随之增加，直到最后一个副本迁移完成，原区域便不再接收任何请求。每个仓库都会经历这一过程：

那么，剩下的 0.00001% 的仓库怎么办？

在当前架构中，如果一个仓库分布在多个区域，其写入吞吐量上限就会降低。Spokes 的仲裁组只需要多数副本同意，就能提交一次写入，但在继续处理下一次写入之前，它会等待每个健康副本响应，直到超时。这样一来，速度慢的副本会拖慢每一次写入，而不是自己落在后面。实际结果就是，最慢的健康副本决定了每次写入的延迟。又因为每次写入都会持有覆盖整个仓库的锁，直到提交完成，所以它也决定了吞吐量的上限。副本一旦迁入目标 Azure 区域，就会与我们的数据中心相距约 1,000 英里，每次网络往返约需 25ms，而一次写入需要多次往返。如果仓库原本就已接近吞吐量上限，就无法在每次串行写入时都承受这份额外开销；每推送一次，积压就会进一步加重。

这时，我们的第一项原则——尽量减少协调——就派上用场了。具体到这里，就是：不需要串行处理的操作，就不要串行处理。Git 的一致性要求分别作用于每个引用。服务器一旦接受了对某个引用的更新，此后任何客户端都不应再看到更旧的值，而只能看到这个值或更新的值。无论这次更新是快进、强制推送还是删除，都必须如此。但在大多数情况下，对不同引用的更新互不依赖，可以独立执行。

因此，我们正在将仲裁组的作用范围从整个仓库缩小到单个引用。

如果在引用更新的全过程中，包括网络往返期间，都持有覆盖整个仓库的锁，仲裁组实际上就成了一个不保证顺序的单一请求队列，同一时间只能处理一次写入。队列中的每次写入，都要花上最慢的健康副本所需的时间。写入速率越高，队列就越长，每次写入等待的时间也比前一次更久。

改为按引用串行处理后，只有争用同一引用的写入才需要相互等待。实际上，一个仓库中的大多数写入操作涉及的是不同引用，例如智能体和开发者各自向自己的分支推送，因此它们不再需要彼此等待。每次写入仍然要承受跨区域延迟，但对不同引用的写入可以同时进行。这就消除了整个仓库共用的那个瓶颈。我们可以在相似负载下并排比较这两种方式，直观地看到排队和超时是如何逐渐累积的：

这些改动让仓库的写入吞吐量上限大致随同时被写入的引用数量成比例提高，也让最后剩下的仓库能够迁入 Azure。在使用贴近实际情况的流量进行的内部测试中，对不同引用的写入持续达到了原来 3–4 倍的吞吐量，同时延迟更低。

大多数仓库的读取操作远多于写入，每写入一次，大约就有 100 到 1,000 次读取。目前，读取和写入访问的是同一批副本，因此会争用相同的资源，也无法独立扩展。

将存储与计算分离，可以改变这一点。只要仓库数据已持久保存到 Azure Blob Storage，并随每次传入的写入而更新，我们就可以开始将读取流量与写入仲裁组分离，独立扩展两者各自所需的计算资源。例如，如果能获得远多于当前配置的内存缓存，读取性能就会受益，但压缩整理也需要这些内存。分离后，两者就可以各自采用适合自己的配置。

第一步是让对象存储成为仲裁组的一员。不过，它是一个特殊成员，我们称之为虚拟副本。代表它的计算节点，是我们第一个完全不保留持久状态的节点。它充当通往对象存储的桥梁，将传入的写入以流式方式传送过去，不处理任何读取。因为它属于仲裁组，所以只有当数据已持久保存到对象存储后，写入才会得到确认。

这会给每次写入增加一点延迟，但与跨区域网络往返一样，按引用串行处理可以防止它成为吞吐量瓶颈。虚拟写副本还会把涉及不同且互不重叠的引用的事务合并起来，用同一组网络 I/O 写入对象存储。因此，繁忙仓库的多次并发写入可以共摊一次网络往返的开销，而不必每次写入都单独往返。目前，虚拟写副本还负责压缩整理，读副本则沿用压缩整理后的状态。

有了虚拟写副本，我们就可以根据需要，为仓库按需扩展任意数量的虚拟读副本。每个读副本都会从 Azure Blob Storage 预热缓存，无需加入仲裁组就能开始承接读取流量。它以对象存储中的数据为准，并在后台与之核对、同步本地状态。

这一步大幅提升了读取的扩展能力。在内部测试中，我们的分布式压测框架经常能测出当前架构的性能上限。而在测试虚拟读副本时，先达到极限的却是压测框架本身。这一步也带来了一些挑战，我们会在后续步骤中解决：

如何进一步提高写入吞吐量？

今天的 GitHub 建立在 Spokes 仲裁组之上。多年来，Spokes 的职责早已不止是协调仲裁。它还是一个智能路由和负载均衡层；它提供统一 API，让内部客户端每天执行远超 1,000 亿次操作，访问仓库数据并进行事务处理；它还包含一组我们称为“清扫器”（sweepers）的后台系统，负责仓库放置、修复，以及存储节点之间的再平衡。

Spokes 服务所涵盖的绝大多数功能，在新架构中与在现有架构中同样适用。但我们也清楚，帮助 GitHub 支撑起十亿个仓库的提交协议，无法再带我们走向下一个十亿，乃至更大的规模。

我们的工作还没有结束。完成这些步骤后，下一个限制就是写入吞吐量。每次写入仍然需要等待那些各自保存着完整仓库副本的节点，但一次写入中真正需要确定先后顺序的内容其实很少。Git 对象不可变，并按其内容命名，因此存储它们时，不需要各方先达成一致。剩下的内容很少，难点在于尽可能快地为其确定顺序，同时避免把瓶颈转移到其他地方。在白板上设计这样的方案是一回事；在十亿个仓库之下实施它，而开发者和智能体还在日夜不停地向这些仓库写入，则是另一回事。为了做到这一点，我们还不得不重新思考由此引发的连带问题，例如引用的持久状态应存放在哪里，以及压缩整理和垃圾回收该如何扩展。

智能体流量的增长没有放缓。上述每一步落地后，都会为仓库释放更多容量余地，无需等到最终形态全部实现。
