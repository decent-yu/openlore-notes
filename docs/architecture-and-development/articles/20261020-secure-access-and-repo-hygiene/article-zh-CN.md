## 原文整理

与外部协作者合作可能会给仓库所有者带来更多工作。你需要确认谁仍然需要访问权限，随着项目的发展调整权限，并在仓库完成使命后将其归档。

为了跟上这些工作，仓库所有者需要跟踪每个仓库的协作者、截止日期和后续跟进事项。随着项目规模扩大，这些手动维护工作会变得越来越难以跟上，也越来越容易被推迟。

我们在一个共享组织中遇到了这个问题。在这里，GitHub 员工（“Hubbers”）与客户和合作伙伴共同开展产品试用和专业服务项目。我们的解决方案是 Evergreen，一个使用 GitHub 原生功能构建的 GitHub App。下面的工作流展示了一种你可以根据自身组织情况加以采用的模式。

认识 Evergreen

Evergreen 是一个 GitHub App，通过两种工作流自动完成组织维护：

外部协作者访问权限复核。每个季度，都会复核各个仓库的外部协作者。保留你需要的人，其余人员全部移除。

闲置仓库检测与归档。超过一定时间阈值没有人工活动的仓库会被标记、收到警告，并在仍然无人操作的情况下被归档。

两项设计原则贯穿始终：

故障时确保安全。如果没有人响应访问权限复核，我们不会保留访问权限并寄希望于一切顺利。我们会撤销权限。安全的结果就是默认的结果。

绝不销毁任何内容。Evergreen 永远不会删除仓库或其中的内容。已归档的仓库可以恢复，而且每一次访问权限变更都会记录在仓库的跟踪议题中，因此撤销错误操作就像向 Copilot 复制粘贴一样简单。

工作原理：一个大脑，多只手

在底层，Evergreen 是一个运行在容器中的小型 Go webhook 服务器。但有意思的部分在于各环节的协同。每一个运作组件都是现成的 GitHub 功能：GitHub App、定时运行的 Actions、webhook、议题、自定义属性，以及仓库中的普通文件。无需重新发明什么特别的东西。

复核会在对应清理任务运行前两周开启，而且内置了不可绕过的宽限期，因此一次意外的手动运行绝不会让撤权提前发生。每个工作流也都支持 workflow\_dispatch，因此我们可以根据需要手动触发任何步骤。

在所有重要环节使用 IssueOps

Evergreen 通过各个仓库内的议题进行沟通。访问权限复核开始时，每个仓库都会收到一条清单议题：

交互方式简单得令人愉快：勾选要保留的人员，然后关闭议题。仅此而已。议题关闭时，Evergreen 会监听 issues.closed webhook 事件，读取复选框，保留已勾选的协作者并撤销其余人员的权限，然后发布一条回执评论，准确列出保留了谁、移除了谁。

只有适当的人员才能执行操作

关闭访问权限复核议题是一项需要特权的操作，因此 Evergreen 会对此进行把关。如果非 Hubber 人员关闭了议题，应用会悄悄将其重新打开，并发布一条说明原因的留言。只有获得决策授权的人做出的决定才算数。

通知适当的人员

这里有一个不易察觉的问题：我们知道需要响应复核的人是 Hubbers，但并不总是知道某个仓库由哪位或哪几位 Hubber 负责。

Evergreen 通过一套逐级回退的规则来确定应当通知谁：

如果仓库设置了 evergreen\_repo\_owner 自定义属性（一个 @user 或 @org/team），就使用该属性。

否则，查看近期议题和提交的作者，并抄送其中属于访问权限复核团队的人员，也就是实际在该仓库中工作的 Hubbers。

结果是：适当的负责人会自动收到提醒，无需任何人维护一张记录“谁负责什么”的电子表格。

故障时确保安全，失败时保持关闭

复核截止日期已过且无人响应时，清理流程会撤销快照中所有协作者的权限。我们仔细处理了一个不易察觉的边界情况：如果一些移除操作成功了，而另一些遇到了暂时性的 API 错误，该怎么办？在仍有移除操作未完成时就将复核标记为“完成”，会造成一种不易察觉的不一致，我们不希望出现这种情况。

因此，Evergreen 会在失败时保持关闭。如果任何移除操作失败，复核就会保持待处理状态，议题也会保持打开，下一次运行时会重试尚未完成的操作。只有在所有移除操作确实成功后，它才会记录为“已撤销”。而且，所有被移除的人员都会记录在议题中，因此恢复访问权限只需重新添加其中列出的用户名即可。

用户体验：体贴的自动化

自动维护向来有着办公室烟雾报警器般的名声：声音大、容易被忽略，而且往往在你正常做饭时响起。我们努力让 Evergreen 带来相反的感受：

它会主动找到你。工作以议题的形式在你的仓库中进行。

它会提及适当的人员。无需翻找历史来弄清“这是谁负责的？”

它会清楚地说明要求。每条议题都会说明需要做什么、确切的截止日期，以及忽略它后究竟会发生什么。

它会先提醒，再行动。截止日期前会发布一条提醒评论：不会突然撤销权限。

它提供了退出机制。组织所有者（Hubbers）可以通过设置自定义属性（evergreen\_exempt\_from\_access\_review 或 evergreen\_exempt\_from\_archive）选择不参与。

谨慎推出

管理访问权限并归档仓库的自动化系统值得谨慎推出，尤其是在规模大且活跃的组织中（我们的组织有 1,400+ 名 Hubbers，以及数量更多的客户和合作伙伴）。我们希望第一次运行完全波澜不惊。以下几项做法帮助我们实现了这一点：

先进行演练。Evergreen 自带 DRY\_RUN 模式，会记录它原本要执行的每一次写操作，而不实际改动任何协作者或仓库。我们在真实组织中运行了它，并像解读茶叶占卜一样仔细研读日志，直到我们信任它打算做出的决定。

充分沟通。在正式启用前，我们广泛告知即将发生什么、何时发生，以及大家需要做什么，以免任何人第一次看到议题时感到意外。我们发现，当你第七次向一大群人讲同一件事时，往往仍有许多人是第一次听到。

用 Splunk 观察一切。Evergreen 会向一个专用的 Splunk 索引输出结构化的 logfmt 日志。正是这种可观测性，让我们捕捉到了实际运行中的边界情况（空的协作者列表、异常权限、禁用了议题的仓库），并在它们造成影响前完善了逻辑。

遵守平台的速度限制。当你在大型组织的每个仓库中创建议题和发布评论时，就会撞上 GitHub 针对内容创建的次级速率限制：80 次请求/分钟，以及 500 次请求/小时。虽然这是一项为防止系统滥用而周全设计的预防性控制措施，但在大规模自动化执行 IssueOps 时，确实需要有意识地加以考虑。

因此，Evergreen 从设计上就会控制节奏。它分批处理仓库，让每次创建内容的调用间隔几秒，并在批次之间暂停，以便滚动时间窗口过去；它只统计实际创建内容的仓库，因此在没有任何仓库符合条件的平静季度，仍能快速运行。我们选择主动避免触发限制，而不是在触发后被动退避。

我们从中得到的经验

让安全路径成为默认路径。在故障时确保安全，再让响应足够简单，使故障安全机制很少需要触发。

使用你已经拥有的基础功能。议题、webhook、自定义属性和 git 历史，完成了原本需要定制界面、任务队列和审计数据库才能完成的工作。

在人们工作的地方与他们互动。仓库中的一条议题，胜过一个你永远不会打开的仪表板。

日志就是撤销按钮。将每次变更写入议题，让“糟糕”变成了“把这三个用户名粘贴到 Copilot 会话中”。

尊重限制。在组织规模下，速率限制不是边界情况，而是设计约束。

让你的组织保持常青

日常维护是一类很容易被推迟、又非常适合自动化的工作。诀窍不在于轰轰烈烈地集中清理，而在于让那些枯燥而安全的事情按计划发生，同时提供友好的体验和一个撤销按钮。

这就是 Evergreen。而且，由于它完全由 GitHub 原生功能构建，你也可以自行搭建同样的模式。

准备好让仓库维护成为例行工作了吗？从一项周期性的访问权限或归档任务入手，再使用 GitHub Apps、Actions、议题和自定义属性，通过自动化消除这个问题。
