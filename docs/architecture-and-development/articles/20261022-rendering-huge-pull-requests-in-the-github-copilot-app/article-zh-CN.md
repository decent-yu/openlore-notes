## AI 导读

文章解决超大 pull request 中代码与评论混排的渲染问题。代码行高度可预先计算，但评论高度受 Markdown 换行、折叠区、回复框和图片加载影响；统一估高再回写布局容易造成留白、裁切和滚动跳动。主要方法是将确定性的代码高度与动态块高度分开索引，动态块通过稳定标识、文件与行侧锚点、内容指纹和宽度分桶复用测量，优先采用有效实测值，其次使用匹配缓存，最后使用估计值。测量集中在受空闲与滚动状态控制的流程中，观察器主要负责标记待测，避免直接写回引发反馈循环；滚动修正还需区分用户操作与界面自身产生的滚动。数据侧采用增量加载、后台语法高亮、临近视口时构建复杂内容，以及有界的近期 diff 缓存。验证侧使用结构化探针、合成大规模夹具、无头流程和桌面自动巡检，检查空白、缺失评论及深层滚动区域。作者称百万行、数百评论的差异视图已可正常打开、滚动并恢复位置。但正文未给出量化性能对比、预算阈值或完整复现材料，且若干规则列表和执行循环缺失，结论主要由工程叙述及自述验证支撑。

### [Alberto Gimeno](https://github.blog/author/gimenete/)

首席设计工程师

我们如何重建 GitHub Copilot 应用的差异视图，让它能够打开包含百万行改动、数百条行内审阅评论的拉取请求。

大范围的重构和迁移往往必须作为一次变更合入。

[堆叠式拉取请求](https://docs.github.com/pull-requests/how-tos/stacked-pull-requests)是将工作拆成较小变更的好方法。这样既便于审阅，也能帮助团队降低交付风险。但有些变更，比如这里的这一个，很难合理拆分。于是，你只能用一个拉取请求承载全部变更，而它可能变得非常庞大，审阅讨论还会让它继续膨胀。

即使差异内容和围绕它的讨论都极其庞大，审阅体验也需要保持快速、流畅。我们正是带着这一要求，重建了 [GitHub Copilot 应用](https://github.com/features/ai/github-app)中的拉取请求视图。

为了看看它究竟能应付多大的规模，我们打开了能找到的最大拉取请求：一个开源项目的拉取请求，涉及 2,200 个文件、超过一百万行改动，以及 400 多条行内审阅评论。下面就来介绍，我们如何让这样极端的拉取请求也能流畅运行。

如何快速渲染大型差异视图，已经有成熟的做法：对行进行虚拟化，控制已挂载的 DOM 规模，并利用每行代码高度已知这一特点。

难点在评论。评论的高度取决于 Markdown 内容如何换行、其中的可展开区域、是否包含回复框，以及图片是否已经加载。这些都要到渲染时才能知道，因此需要一套不同的架构。

三个问题：

第一步是理解，只有代码的差异视图为什么能依靠尺寸和位置计算实现快速渲染。一旦加入评论，原有的计算方式就不够用了。

你不可能在一个页面上放一百万个 DOM 节点。标准答案是**虚拟化**：只挂载屏幕上可见的行，再加上少量缓冲区域，并在用户滚动时复用这些 DOM 元素。列表的表现就像一百万行全都存在一样：滚动条的大小正确，也能滚动到指定行。但实际上，任何时刻真正存在的都只有大约 100 行。

要维持这种效果，就必须有一套尺寸和位置数据作为支撑。滚动条所代表的内容总高度，是所有行高度的总和。第 *N* 行的位置，是它上面所有行高度的总和。跳转到某一行、绘制滚动条、判断屏幕上有哪些内容，本质上都是基于一张行高表进行计算。你可以先用估计值建立这张表，再随着各行完成测量逐步修正。通用的可变行高虚拟化组件正是这样做的。

但如果每一行都是字号已知的代码，就不必如此。你可以提前算好整张表，而且它永远不会变化，因此后续也就无须修正。

我们把它称为“绘制前已知所有高度”的约定。我们的差异视图就是围绕这个约定构建的：

这些设计都不会因规模扩大而明显恶化，因为每一帧的工作量都不会随总行数增加。对于纯代码内容，这套设计是合适的，因此我们将它完整保留了下来。

现在，在差异视图中间放入一个审阅讨论串。它有多高？

你不知道，不把它渲染出来也不可能知道。它的高度取决于只有渲染时才会确定的因素，而且在首次绘制之后，这些因素还可能继续变化：

用户可以直接展开或折叠的 `<details>` 区块。

最直观的办法，是根据估算器的结果，为每条评论预留一个固定高度的区域。但这种办法在大型拉取请求上行不通。估算器即使平均来看很准确，在极端情况下也仍然会出错。它为大多数评论预留了过多空间，留下大片空白；又为那些需要更多空间的评论预留不足，导致内容被裁切，或者出现嵌套滚动条。如果在绘制后测量实际高度，再将结果写回共用的偏移量表，下方所有内容都会移动，**而此时用户已经在滚动了。**这就造成了滚动位置跳动，而且在大型拉取请求上，跳动幅度会很大。

因此，评论需要另一套约定。对这类内容来说，“绘制前已知所有高度”是不可能实现的。我们能承诺的是：高度有界，按需测量，修正幅度小，并且以用户正在查看的内容为锚点。

让这个问题变得可解决的关键，是不再强求两类内容共用一套尺寸和位置计算方式。我们将文档高度拆成了两个彼此独立的部分：

```
total height = deterministic code height          (exact, known up front)
             + Σ dynamic block effective heights   (estimated, then measured)
             + scroll padding
```

**代码布局计算**保留原有方式。它是确定的，通过前缀和计算，结果精确，而且不会因为某条评论尺寸变化而重新构建。

**动态块布局计算**负责所有无法预测高度的内容，例如审阅讨论串、草稿和回复编辑框。每一项都是一个块，其标识取决于它是什么，而不是当前位于哪里。每个块都有稳定的键，内容加载前后都不会变化。它锚定在某个文件的某一行及其所在侧，而不是某个像素坐标，因此即使布局重排，也不会丢失它的位置。我们还会为所有可能影响块高度的因素保存指纹，包括内容、`<details>` 是否展开，以及编辑框是否处于启用状态。此外，我们会记录上次测量时的宽度，并将宽度归入若干区间。这样，普通的窗口尺寸调整就不会让整份文档的测量结果全部失效。

由此，一个块的有效高度很容易确定：如果有有效的实测高度，就用实测值；如果内容指纹和宽度仍然匹配，就用缓存高度；否则使用估计值。这些高度保存在独立的索引中，与代码行分开，因此评论尺寸变化永远不会迫使代码布局重新计算。而且，块的数量取决于评论数量，与代码行数无关。几千个块没有问题，前提是首次绘制时不能一次性挂载或测量所有块。

这一部分花了最长时间才做对，因为我们的第一个设计犯了一个很有启发性的错误。

测量动态内容，最直观的做法是给每个块配一个 `ResizeObserver`，观察元素，并在尺寸发生变化时，将测得的高度写回布局。我们最初就是这样设计的，后来在性能优化阶段否定了它。大型虚拟化视图必须避免的，正是这种反馈循环。如果观察器将高度写回它所观察元素的布局，就可能再次触发自身，而且成本会随着已挂载块的数量增加。

最终上线的方案，是一个统一的测量流程。它根据空闲状态和滚动状态决定何时运行，并遵循与确定性布局部分相同的严格约束：

仍然使用 `ResizeObserver`，但默认情况下，它只负责给块打上标记，让空闲时的测量流程重新读取。它自身绝不写入高度，因为一旦写入，就会形成我们之前否定的反馈循环。块卸载时，观察器会断开连接；未激活的拉取请求标签页不会观察任何元素。

最后那条规则有个棘手的边界情况，我们也确实栽在了这里。我们实现“用户正在滚动时不做修正”时，用最近一次观测到的滚动时间作为判断依据，但程序触发的滚动也会刷新这个时间戳。切换文件树侧栏的显示状态，会改变差异面板的宽度。开启自动换行时，你上方每一行发生换行的代码都会重新排版，占用的显示行数也会变化，整个坐标空间随之移动。视图在布局稳定下来时，还会自行触发一次小幅滚动。保护逻辑把它理解成“用户刚刚滚动过”，于是跳过了本应用来保持阅读位置的修正，导致你正在阅读的文件移出了屏幕。修复办法是区分用户触发的滚动与视图自身触发的滚动。任何用于判断“用户是否正在交互”的检查，都不能被你自己的副作用触发。

这样，修正幅度就能保持很小，既能复用已有测量结果，也能始终跟随你正在查看的内容。

差异视图能有多快，也取决于为它提供数据的过程。这部分工作中的三个做法，决定了界面能够实现什么。第一个是先逐步提供结构，再提供内容。差异数据采用增量请求，因此文档还在加载时，文件树和元数据就能绘制出来；完整的审阅讨论串则会预先解析就绪，而不是零零散散地陆续出现。第二个是将每一项的处理推迟到真正需要它时。语法高亮在主线程之外运行，因此代码行会立即以纯文本显示，结果返回后再加上颜色。高亮是在改善视图，而不会阻塞滚动。大型 Markdown 正文和修改建议的上下文也采用同样的方式：只有接近视口时才开始构建。

第三个做法关乎哪些成本值得保留下来。离开页面时释放差异文档，是合理的默认选择。这些文档很大，如果保留你访问过的每一份文档，长时间使用后就会占用大量内存。但拉取请求的元数据会保留，因此当你返回时，差异视图外围的界面、页头和文件树都能立刻重新绘制，随后却要在那里等上几秒，等待一份片刻之前还完整存在的差异文档。即便整体等待时间已经缩短，一个瞬间画好、里面却空空如也的差异视图外壳，仍会让人觉得出了故障。所以我们保留了原有策略，同时加入缓存：让最近几个差异文档常驻内存，超出数量的就淘汰，再由后台刷新检测其中哪些已经过期。

这个项目里几乎每个缺陷，都是在特定时刻才突然显现，而且手动复现非常痛苦。典型的问题报告是这样的：“某些评论下面会出现一条空白，但只是偶尔出现，只在大型拉取请求中出现，而且滚过去再滚回来就好了。”光盯着屏幕看，没法调试这种问题，所以我们构建了工具，以自动化方式调试。

最直观的工作流程，是到处插入 `console.log`，手动走一遍操作流程，复制输出，粘贴给能够分析它的人或工具，再删除日志，如此反复。这个过程很慢，需要人参与。最糟的是，最后你测量到的往往是自己临时编写的监测代码，而不是应用的真实行为。

因此，视图内置了长期保留的结构化探针，用来检查自身应始终满足的条件。每次渲染时，它都会回答一些关于自身的简单问题：

这些就是客观的通过或失败信号。我们将它们设为端到端测试中的预算阈值，使用人工构造的、带有大量评论的超大拉取请求测试数据进行断言。现在，CI 可以告诉我们视图是否运行正常。

其中最核心的是一个自主运行的**修改 → 测量 → 改进**循环，分为两条执行路径：

**无头探测路径**在模拟服务器上运行声明式流程，例如打开拉取请求、滚动到某个比例位置、切换详情区块的展开状态，以及调整窗口大小。它读取应用在生产环境中使用的监测数据，包括 React 渲染次数、性能时间线，以及用于检测卡顿的 `requestAnimationFrame` 采样器。它会自行完成监测、驱动操作、收集数据、分析和排序的全过程，并按顺序输出性能瓶颈。由于流程只是运行时交给探针的一份 JSON，智能体只要用自然语言描述操作，就能对任何流程进行性能分析，无须修改任何源代码。

**自动驾驶程序**则无人值守地操控实际的桌面应用，循环执行超大拉取请求的操作流程：先在冷状态下运行，此时评论仍是骨架占位；再在评论已加载的热状态下运行。操作包括切换 `<details>` 区块的展开状态、打开和取消回复编辑框、折叠和展开文件、切换侧栏文件树、遍历文件列表深处的内容，以及调整窗口大小。每次测量都会同步写入应用的磁盘日志，因此即使无人操作键盘，智能体也能读取运行时行为。每个样本都带有一个健康状态信号，它就是客观的检查依据。热状态样本只有满足以下条件才算正常：在整个滚动范围内，包括文件列表深处的遍历区域，评论之间都没有未填满的空隙，没有评论块保持空白，并且真实的讨论串内容确实已经挂载。

过去，审阅这么大的拉取请求只有两种结果：一直等，或者放弃，换个地方阅读。代码审阅不是一份尺寸固定的文档，而是一场在阅读过程中不断改变形态的对话。承载它的视图从一开始就必须为此设计，而不能事后再打补丁。

最终得到的拉取请求视图，能够像处理普通规模的拉取请求一样，打开和滚动包含百万行差异、数百条讨论串评论的拉取请求，并正常响应操作。评论会完整显示，不会被裁切到一个可滚动的框里。展开折叠区域时，只有它下方的代码会移动，其他内容不受影响。返回刚刚离开的拉取请求时，你仍会停留在原先的位置。
