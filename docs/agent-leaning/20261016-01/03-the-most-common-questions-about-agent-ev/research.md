# 从单元测试到环境断言：生产级 AI Agent 评测的工程架构与落地实践

在大语言模型应用从单纯的单轮补全走向具备自主规划、工具调用与长程执行能力的 AI Agent 阶段，传统软件工程的质量断言体系正在遭遇根本性失效。传统单元测试依赖“输入确定则输出恒定”的严格等值断言，而智能体系统天生具备输出非确定性、解法多样性以及执行路径自主选择三大特征。一个最终回复看起来正确的智能体，可能在底层经历了高冗余的工具调用、越权操作甚至脏数据写入。

要让智能体在生产环境中稳定运行，核心工程解法在于构建“离线基准评测（Offline Evals）与线上实时质检（Online Evals）双向互哺”的闭环架构：在发布前通过固化数据集和容器化沙箱执行基准回归，在发布后对真实流量进行低成本抽样监测，并将线上捕获的失败链路沉淀为新增测试集。评测策略应当坚持确定性代码断言优先、二元判别式大模型裁判（LLM-as-a-Judge）兜底、人工队列校准标尺，并将验证对象从最终文本逐步推进至多轮执行轨迹（Trajectory）与沙箱环境终态（Environment State）。

## 传统单测为什么失效与评测粒度的四层推进

传统测试框架之所以难以直接套用于智能体，根源在于智能体行为模式的三个不确定维度：
1. **输出表达的不确定性**：即使底层模型温度设为 0，自然语言回复的遣词造句依然存在随机性，直接使用字符串全等匹配或简单正则表达式极易产生误报。
2. **正确解法的多样性**：对于“规划行程”或“修复代码”等开放式需求，存在多条同样合理的达成路径，单一参考答案不足以覆盖有效输出空间。
3. **执行路径与终态割裂**：智能体具有选择工具和调用步骤的自由度。即使给出的最终文本答复完全满足要求，中间步骤仍可能调用了多余的高成本工具、泄露了敏感数据，或在无授权的情况下修改了外部系统。

针对上述特征，智能体评测不能停留于黑盒端到端比对，而需要依据工程复杂度划分为四个推进层级：

| 评测层级 | 核心关注点 | 典型检验手段 | 适用场景 |
| :--- | :--- | :--- | :--- |
| **单步调用 (Single Step)** | 单次工具入参、函数选择的准确性 | 参数 Schema 校验、确定性代码断言 | 工具选择与参数提取的准确率验证 |
| **最终回复 (Final Response)** | 模型最终输出对用户意图的满足度 | 无参考 LLM 裁判、事实一致性比对 | 单轮问答、结构化总结交付 |
| **多轮轨迹 (Full Thread)** | 跨轮次意图继承、步骤冗余度、无意义循环 | 轨迹回放比对、多轮上下文相关性评分 | 复杂客服、多轮修改型业务助手 |
| **环境终态 (End State)** | 外部系统真实副作用（数据库记录、代码产物） | 容器内测试脚本、状态快照 Diff | 编码智能体、运维智能体、自主任务调度 |

将评测重心从单纯的“最终文本”推向“多轮轨迹”与“环境终态”，是区分玩具 Demo 与生产级智能体工程的关键分水岭。

## 双环架构：离线基准回归与线上流量监测的互哺机制

一套健壮的评测系统并非单点脚本，而是一套贯穿研发与运维全周期的双环反馈流。

离线评测（Offline Evals）在变更发布前运行，其核心输入是确定性的数据集（Dataset）。数据集由一组输入用例构成，通常附带基准参考输出或预期行为说明。离线评测的主要价值在于建立基线实验（Baseline Experiment），在新提示词、新模型版本或新工具注册引入时执行横向对比，在代码进入生产前拦截质量退化。启动离线评测无需成百上千条测试用例，从团队内部试用或线上抽样的 10~20 条真实 Trace 切入即可建立最小可行闭环。

线上评测（Online Evals）则挂载在生产流量之上，对实时产生的 Trace 进行流式打分。由于生产请求不存在预置的参考答案，线上评测高度依赖无参考（Reference-free）评估器与确定性代码检查。线上评测的核心职责在于质量监控与缺陷捕获。

离线与线上的连接点在于数据回流：线上评测捕获的用户点踩、裁判未通过或异常中断的 Trace，经由标注队列人工审查或异常聚类引擎整理后，直接作为新用例注入离线数据集。这形成了“发现缺陷 -> 固化为用例 -> 改进智能体 -> 离线回归验证 -> 安全发布”的工程飞轮。

在数据集管理上，工程团队需遵守清晰的裂变边界：
- **同数据集维护**：当用例属于同一业务行为且使用相同的一组裁判器时，保持在同一个数据集中，确保实验版本间的评分具备历史可比性。
- **独立数据集拆分**：当输入结构发生根本改变（如单轮请求扩展为多轮长对话）、需要挂载完全不同的评估逻辑，或用途不同（如每次 Pull Request 运行的 10 条高危核心回归集，对比发版前运行的完整压测集）时，必须拆分独立数据集。

## 裁判器选型矩阵与低成本可靠评测设计

在评测执行器（Evaluator）的落地选型上，团队面临吞吐量、确定性、语义理解力与成本之间的权衡。

| 裁判器类型 | 运行成本 | 判定延迟 | 结果确定性 | 核心优势与局限 |
| :--- | :--- | :--- | :--- | :--- |
| **确定性代码 (Code)** | 接近为零 | 毫秒级 | 100% 确定 | 速度极快、无幻觉；仅适用于结构化数据与确定性断言 |
| **二元大模型裁判 (LLM Judge)** | 中到高（受模型规模决定） | 秒级 | 存在概率漂移 | 能理解自然语言语义与上下文；需防范提示词漂移 |
| **人工标注审查 (Human Review)** | 极高（纯人力） | 分钟至小时级 | 主观真实基准 | 评价语义与业务体验的最高信源；吞吐受限，用于标定对齐 |
| **成对对比 (Pairwise)** | 双倍模型推理成本 | 秒级 | 依赖排序判断 | 消除绝对评分偏差，擅长模型 A/B 择优；无法直接给出绝对及格线 |

为了建立高置信度的 LLM 裁判，工程实践中必须贯彻三项原则：
1. **人工抽样标定与 Prompt 迭代**：定期抽取部分评测样本由工程师或领域专家打分，计算 LLM 裁判与人工打分的一致率。当裁判判定发生分歧时，将分歧案例作为少样本示例（Few-shot）补充进裁判 Prompt 中。
2. **拆解窄域原子问题**：避免向裁判提出诸如“这个回答是否足够优秀”等抽象、主观的问题；将其拆解为客观可判定的原子命题，例如“回答中是否明确确认了用户要求的每一个经停城市”。
3. **强制离散化标尺**：坚决摒弃 1~10 分的连续数字打分制。大模型在连续分值区间上的判定方差极大，难以稳定区分 6 分与 7 分的边界。生产裁判应当统一收敛至二元布尔值（Pass / Fail）或少量互斥的标签分类枚举。

针对线上流量评测的账单爆炸风险，成本控制策略可采用三级过滤机制：
- **流量抽样与触发式质检**：仅对全网 5%~10% 的日常请求执行评测，或仅在用户触发负面反馈（如点踩、重试、打断）时挂载深度裁判。
- **确定性代码优先过滤**：在调用 LLM 裁判前，先执行代码检查（如响应是否包含必选字段、预订金额是否超预算）。未通过代码检查的 Trace 直接标记失败，不再消耗模型 Token。
- **分级裁判模型路由**：不宜盲目使用旗舰大模型担当通用裁判。根据实际基准测试，在二元 Pass/Fail 分类任务中，轻量级专用判别模型能够取得与顶级大模型相当的人工一致率，而评测成本可相差两个数量级（例如特定实验中轻量判别裁判总成本仅为 0.34 美元，而调用顶级商用模型处理相同集则耗费 28.17 美元）。

## 容器化基准测试：Harbor 与环境终态断言

当智能体具备编写代码、执行 Shell 脚本、读写文件系统等复杂系统交互能力时，基于文本和元数据的传统评测便触及了天花板。此时评测必须向基准测试（Benchmark）演进。

基准测试与常规单次评测的核心区别在于三个要素：
- **长执行步长**：单任务包含数十次交错的命令执行、文件检索与状态修正。
- **环境隔离**：每个任务必须在独立的沙箱容器（如 Docker）中启动，配备完整的运行依赖、初始代码仓与测试环境，避免用例间的状态污染。
- **状态验收断言**：评分核心不看智能体在对话框中说了什么，而是由容器内的验收脚本直接检查系统终态——代码修改后的单元测试是否全部跑通、目标文件是否存在且格式合规、数据库状态变更是否符合预期。

在开源生态中，Harbor 等评测线控工具（Eval Harness）正是为这种长步长容器化评测而设计。它为每个任务编排独立的容器环境，驱动智能体在沙箱内完成多轮工具调用，并在执行结束后运行宿主验收脚本判定胜负，最终将执行 Trace 与终态结果上报至平台统一记录。基于这一架构，团队可进一步搭建类似自动科研循环（Auto-research Loop）的自动化调优链路：自动化执行提示词或工具链微调、批量跑批基准测试、依据通过率指标自动决定是否采纳变更。

## 生产落地路线图与工程排障清单

智能体评测体系的建设切忌一步到位，推荐遵循以下阶梯式演进路径：

第一阶段（埋点感知）：在现有智能体代码中接入标准化追踪（无论是使用 OpenAI Agents SDK、Claude Agent SDK 等开源框架，还是自研应用直接挂载函数级 `@traceable` 装饰器），确保请求输入、输出、中间大模型调用与工具入参能够完整落盘为 Trace。

第二阶段（基线建立）：从内部试用日志中挑选 10~20 条典型行为链路，构建首个回归数据集，并执行首次实验固化为团队基线指标。

第三阶段（代码与二元裁判落地）：编写首批低成本确定性代码校验函数，搭配 1~2 个窄域二元 LLM 裁判，接入 CI/CD 流程作为 Pull Request 的自动化拦截门禁。

第四阶段（沙箱状态验证与飞轮闭环）：针对涉及生产环境变更的高危智能体，引入容器化沙箱 Harness 执行终态断言；在线上配置异常采样，让生产错误自动沉淀为回归测试用例。

在评测体系日常维护中，建议依照以下排障清单自检：
- 裁判器打分结果波动剧烈：排查是否使用了 1~10 分标尺，改为二元 Pass/Fail，并检查裁判 Prompt 是否提供了清晰的判别标准与正反例。
- 离线评测全绿但线上用户反馈频繁翻车：排查离线数据集分布是否失真，是否有针对性地收录真实失败 Trace；检查评测是否仅断言了最终回复而遗漏了中间执行路径与副作用。
- 线上评测 Token 账单过高：检查是否全量开启了昂贵裁判；关闭全量检测，转为 5% 采样率，并优先使用确定性代码做前置过滤，将大模型裁判路由至轻量专用模型。
- 评测耗时阻碍研发发布：将大型评测集拆分为“PR 快速验证门禁集（10~15 个高危用例）”与“发布全量回归集”，在持续集成阶段实施分级验证。

建立严谨的评测工程，是智能体应用从原型走向规模化商用的必经之路。唯有摆脱对黑盒输出的直觉依赖，以确定性的 Trace 为依据、以分层裁判为标尺、以沙箱环境状态为终审准则，才能在模型与业务的持续演进中构筑起坚实可靠的质量护城河。
