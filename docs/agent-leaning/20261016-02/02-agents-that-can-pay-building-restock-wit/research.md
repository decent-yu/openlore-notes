**让智能体付款：从 Restock 看授权、预算与订单状态的工程边界**

让采购智能体找到商品并不难，难点是让它在用户认可的范围内动用真实资金。Restock 给出的核心思路，是把商品搜索、购物车编排交给模型，把支付凭据、金额约束、人工批准和成交确认交给受控工具及外部系统。这个基于 Slack 的办公用品采购样例说明：可靠的支付能力依赖明确的权限边界，以及从报价到履约的状态管理。

本文仅依据所提供的文章全文分析；涉及实现细节的建议属于工程推论，未查阅源码或独立运行样例。

Restock 的架构有四个分工。Managed Deep Agents（MDA）托管智能体，负责 Slack 接入、会话状态、凭据连接和人工审核；Zinc 搜索商品并代为向零售商下单；Link 保存用户支付方式并取得付款同意；Machine Payments Protocol（MPP）组织 HTTP 层的支付交换。模型通过搜索、准备订单、设置金额、请求付款、等待批准、查询订单等工具推进任务。这样的工具拆分，为每个业务阶段设置了可检查的入口。

MPP 的基本流程是：客户端发起请求，商家返回 `402 Payment Required` 及支付要求，客户端取得支付凭证后重新提交。Restock 在审核前先发起不带支付凭证的订单请求，从挑战响应中读取实际费用；之后向用户展示费用和预付金额，再完成授权与付款。这使支付要求来自交易接口，而非模型依据商品页面估算。代价是覆盖范围：只有支持 MPP 的 API 才能接入这条路径，浏览器结账可以覆盖更多网站，却要承担页面变化和自动化受阻的问题。

理解这套设计，首先要区分预算、预付款、零售商可用额度和最终净支出。原文的示例预算为 25 美元，用户选择预付 23 美元；扣除 Zinc 的 1 美元基础费，商品、税费和运费只能使用剩余的 22 美元。零售订单最终花费 21.18 美元，加服务费后的净支出为 22.18 美元，多付的 0.82 美元退回。上述价格是说明性数字，不是成本基准。

预付机制把税费、运费尚未确定的问题，转化为一个有上限的资金安排，但它并未消除价格不确定性。预付金额较低，可能不足以覆盖最终费用；预付金额较高，则会暂时占用更多资金。可选服务费还会压缩商品额度。因此工程上应同时展示批准金额、服务费用和可用于零售订单的余额，并把退款进度作为独立状态呈现。原文没有说明超额后的具体处置、退款时限与失败恢复策略，这些能力仍属未知。

授权分为两层。第一层发生在 Slack：用户审核购物车、办公室标识、费用和预付金额，MDA 通过中断暂停运行，等待用户点击批准或拒绝。原文明确指出，模型写入工具参数的内容不能代替这个批准。第二层发生在 Link：用户打开授权链接，在钱包页面同意支付 Zinc 挑战要求的确切金额。Slack 审核对应采购意图，钱包授权对应资金使用，两者承担不同职责。连接钱包只建立可复用的会话，不等于同意购买。

这里最关键的约束是，付款凭证本身不能保证购物车符合审核内容。原文明确说明，Link 的共享支付令牌不会自行约束购物车细节，因此支付工具还会核对订单与已审核内容是否一致，并确认批准仍然有效。由此可以推导：必须在实际提交交易的位置检查授权，单靠提示词要求模型遵守预算并不足够。原文未披露校验字段、有效期和并发控制，无法据此断言所有修改或重复提交都已被防住。

可复用的实现建议是：批准时保存不可由模型随意改写的订单快照，至少关联商品、数量、费用、金额、配送目标和申请人；提交付款前，将当前请求与快照核对。商品替换、数量增加、费用变化或配送目标变化，都应触发重新审核。钱包授权也应关联同一交易版本，避免用户批准的是一个版本，工具提交的却是另一个版本。这是对原文校验思路的工程扩展，并非已经核实的源码行为。

凭据隔离同样依赖执行环境。Restock 把 Link 会话保存在用户所有的 MDA Connection 中，使不同人的钱包各自归属；配送地址、通知邮箱和 Zinc API 密钥则放在智能体所有的 Connection 中。辅助程序仅在命令执行期间把钱包会话放入沙箱。支付工具从私有沙箱文件读取令牌，用后删除，只把公开摘要返回模型。模型因此无需接触卡号或支付令牌，也不必在对话中传播这些秘密。

不过，隔离模型可见内容只是安全边界的一部分。工具日志、异常信息和沙箱访问权限仍需单独治理；删除临时文件也不能证明日志中没有副本。实践中应限制工具返回字段，对错误输出脱敏，并核对当前申请人与钱包连接的归属关系。另一个容易遗漏的成本入口是搜索：原文说明，Zinc 搜索依赖预充值账户，不通过 Link 付款。因此，单笔采购预算不能直接代表智能体的全部运行成本，还应为搜索调用设置独立额度和频率限制。

支付成功与订单成立也必须分开。Restock 只有在 Zinc 返回 `order_placed` 后才向 Slack 确认下单，发货后再提供物流信息。这体现了状态来源的分工：钱包确认付款同意，支付系统处理资金，商家接口确认订单。客户端超时并不能证明下单失败；若立即重试，可能产生重复交易。工程上应保存交易关联标识，先查询既有请求状态，再决定是否重试，并确认接口的幂等能力。原文没有给出这些恢复机制的实现证据。

这套方案适合商品范围明确、用户可以逐笔批准、供应商提供机器支付接口的采购助手。样例仅支持美国配送、美元结算、每次部署一个办公室，使用申请人自己的钱包。企业统一付款、多办公室权限、跨币种结算或无人值守补货，都超出了已展示的能力范围；要用于这些场景，必须补充账户归属、组织审批和对账设计。

落地时可沿用原文的三阶段路径：先用演练模式检查对话和状态流转，再用 Link 测试批准模式验证真实搜索与钱包授权，最后进行小额真实采购。原文作者报告曾在托管部署中完成真实下单并收到预期退款，但这不足以证明高并发、异常恢复或长期运行表现。验收应围绕具体边界展开：拒绝后能否阻止付款，审核后改价能否要求重新批准，超时后能否避免重复下单，以及退款能否与原交易对应。把这些约束落实到工具和交易状态，才能将一个会采购的演示转化为可运营的系统。
