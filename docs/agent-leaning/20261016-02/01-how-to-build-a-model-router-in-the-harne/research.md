# 把模型路由放进 Agent 执行框架：成本优化如何受质量约束

编码 Agent 的成本问题，常常来自把能力需求不同的任务全部交给最强模型。模型路由的核心，是在任务成功率约束下选择更经济的执行模型。LangChain 的 Open SWE 实验提供了一个具体样本：按线程选择模型后，单线程成本中位数下降约 64%，PR 合并率未观察到统计显著变化。但这只能支持在该任务分布下继续验证路由，不能证明质量完全等价，也不能直接推导出其他团队的节省比例。

路由首先依赖对真实任务的理解。原文团队分析了一周的交互线程，用 LLM 根据标题和元数据分类；新功能占 22%，修复缺陷占 17%，测试或无实际变更的运行占 16%。他们还观察到，功能调查通常更长、更贵，测试和发布流程相对简短。这些数据支持“部分请求可以使用较便宜模型”的假设，却不足以形成“测试任务一律走低档”的规则：类别描述工作目的，不能完整表达依赖范围和推理难度。

成本和调用次数也只能作为复杂度的代理信号。原文指出，调用多可能意味着任务困难，也可能意味着模型需要更多追问才能完成。从工程分析看，成本还受输入长度、模型价格和重试影响。因此，建议把任务标签与修改范围、验收条件、失败记录一起分析，避免把当前系统的低效行为误当成任务本身的难度。

原文实现的数据流很短：线程首条用户消息进入分类器，分类器结合基础提示词和各档标准，输出模型档位；Agent 中间件据此选择模型，后续整条线程沿用该选择。基础提示词要求选择可能完成任务的最低成本模型，各档标准则结合本地任务分析与厂商能力说明制定。最初版本使用 LLM 结构化输出，后来改用 Jev 决策模型。原文称分类速度提高近 50 倍，但没有给出绝对延迟和完整测试条件，不能据此估算整个 Agent 的提速幅度。

这个设计解释了为什么路由适合放在 harness，即负责组织提示词、工具和执行流程的框架层。相同的“修复登录问题”，在只读问答系统和能够修改多服务代码的 Agent 中，含义不同；执行框架知道任务允许做什么、怎样才算完成，更适合维护领域化的分档标准。通用网关仍可处理凭证、配额和供应商连接。这里的架构判断是让任务语义决定模型选择，再由基础设施完成调用。

不过，必须区分框架拥有上下文与分类器实际读取上下文。原文明确描述的输入是首条用户消息，并未说明分类器读取了完整仓库、工具结果或后续调查信息。因此，这是一种依赖初始描述的预测。描述简短、约束隐含或调查后才暴露跨模块依赖的任务，都可能被低估。将路由放进执行框架为丰富决策信号提供了位置，并不自动保证分类准确。

候选模型同样需要本地验证。原文按成本、速度和能力配置 fast、balanced、performance 三档，具体采用 GLM-5.3-Flash、GPT-5.6 Sol 和 GPT-6 Astra，并设置不同推理强度。通用榜单可以帮助缩小候选范围，却无法替代对工具调用、长上下文和本地代码任务的评估。上述配置仅是输入材料报告的实验选择，本文没有外部核查其当前供应状态、价格或排名。

三档结构的价值在于减少决策空间：先判断任务落在哪类能力区间，再映射到具体模型。统一模型接口降低了替换接入代码的成本，但接口兼容不代表行为兼容。建议更换任一档模型时，复核工具参数、上下文限制、错误恢复和验收表现，并为路由规则与模型配置保留版本，使成本或质量变化可以追溯。

原文最有价值的证据来自覆盖 973 条线程的 A/B 测试。路由组与始终使用最强模型的对照组，PR 合并率分别为 29.2% 和 27.3%，p 值为 0.49；PR 创建率分别为 38.9% 和 39.6%，p 值为 0.82。线程成本中位数从 2.61 美元降至 0.94 美元，均值下降 42%，第 90 百分位下降 37%。这表明节省同时体现在典型线程、平均开销和较高成本位置，不能把中位数降幅直接当成总账单降幅。

质量结论需要更谨慎。统计不显著不等于已经证明非劣效；原文未提供预设的可接受退化幅度或完整置信区间。合并 PR 还受任务类型、需求变化和评审行为影响，无法直接衡量不产生 PR 的问答质量。稀疏的点赞、点踩反馈能够暴露误路由，却不足以代表全部用户。建议同时记录任务类型、完成状态、人工修订和失败原因，尤其防止总体指标掩盖某类复杂任务的退化。

路由组中，56% 的线程进入 balanced，34% 进入 fast，只有 10% 使用 performance。各档线程成本中位数分别约为 1.50、0.097 和 2.88 美元。这些数字反映的是分流后的结果：不同档位承接了不同任务，不能把约 30 倍的成本跨度解释为同一任务切换模型就能节省相同比例。另一次与全部使用 fast 的比较因用户反馈质量问题而在一天内停止，尚无统计有效结论；它提示统一降档存在风险。

线程内固定模型是一项清晰的取舍。它减少路由调用和切换状态，也便于归因，但无法应对“先咨询、后要求修复”这类需求升级。原文将中途重路由列为后续方向，并指出切换模型会失去原模型的提示词缓存收益；异步交互中，如果缓存已经过期，额外损失可能较小。实际影响取决于供应商缓存机制、线程长度和交互间隔，材料不足以给出统一阈值。

可落地的改进是先加入少量可解释的升级触发条件，例如任务目标改变、用户补充跨服务约束，或同一验收项连续失败。以上属于建议，并非原文已实现功能。是否升级应比较预期成功收益与重新读取上下文、增加延迟及恢复执行状态的成本；频繁切换未必经济。原文还说明子 Agent 当前独立选模，因此主线程路由并未覆盖全部执行路径，后续优化需要把子任务支出纳入观察。

实施时，建议先建立覆盖本地主要任务的固定回放集，保留原有强模型基线，再以有限流量观察结果。路由日志至少记录首条请求、规则版本、选中档位、分类耗时、线程费用和验收状态。对高风险或信息不足的任务采用保守档位，并提供人工升级入口；调整规则时重点复盘低档失败与高档无必要使用的样本。这套方案更适合任务种类丰富、能够收集结果的 Agent。流量很少、任务高度同质或错误代价极高的系统，应先判断节省是否足以覆盖分类、评估和维护成本。

本文仅依据提供的全文分析，未联网核查、遍历源码或运行实验；未披露的分类准确率、延迟分布和长期质量变化仍属未知。
