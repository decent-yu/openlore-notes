# 领域专家如何沉淀为软件基础设施：高危 AI Agent 的评估工程学实践

在医疗、金融与合规等容错代价极高的业务场景中，验证 AI Agent 输出质量的核心瓶颈不在算力，而在领域专家的稀缺工时。临床医生能一眼看出一段由语音生成的病历是否准确归因了症状，或者智能导诊是否给出了恰当的转诊级别；但没有任何一家机构能够承受让资深医生持续审查数万次真实问诊。若每次模型或提示词迭代都依赖人工抽样排查，评审工时会迅速成为研发阻塞点。Abridge 与 Included Health 的实践揭示了一条清晰的工程路径：必须停止将专家审查视为重复发生的操作支出，而是通过结构化标注、自动校准评测器与分级灰度门禁，将临床判断沉淀为可持久复利的工程基础设施。

## 1. 专家审查的边际成本陷阱与范式转移

传统软件测试依赖确定性的断言函数，但生成式医疗系统的输出具有高度上下文依赖性与非结构化特征。Abridge 的核心场景是将医患对话转录并结构化为临床病历，用于后续病程追踪与医保计费；Included Health 则基于 LangGraph 与 Deep Agents 构建了导诊助手 Dot，用于解析会员模糊需求、解答报销政策并识别急诊风险。

这两类场景面临相同的可靠性约束：“信任在几滴水间建立，在整桶水里倾覆”。一旦系统出现主诉与诊断归属倒置，或者漏诊了高危急腹症，将直接引发医疗或合规事故。过去，团队在每次发布前组织医生突击评审，这种“作坊式验证”导致两个严重后果：其一，发版周期被拖长至 1 到 2 个月；其二，单次评审结论随版本更迭直接作废，后续迭代依然需要重新人工核对。

解决该矛盾的核心，是将专家审查在软件生命周期中的角色彻底重构。研发团队不能指望用大模型完全替代人类医生，而是要将单次专家评审转化为可自动回归的机器评测器（Evaluator）、黄金基准数据集（Dataset）与自动化阻断门禁（Release Gate）。

## 2. 临床判断资产化的三道工程门槛与机制解耦

要将专家的隐性经验编码为自动化资产，必须首先解构临床判断的特殊属性。根据一线业务反馈，传统的静态字符串比对或简单的 LLM-as-a-judge 在医疗场景中存在三项内生缺陷：

首先，真实临床并不存在唯一的“标准答案”（Ground truth is rarely singular）。不同专科、不同年资的医生在病历书写风格、术语详略上均有合理差异。若将某一份参考病历设定为唯一真值，会导致系统误罚合理的表述变体，却放过隐藏的医学逻辑漏洞。

其次，“正确的不作为”与“正确作为”同等重要（Correct inaction matters）。在导诊场景中，急诊安全拦截器在识别心梗征兆时必须果断触发，但在良性咨询中必须保持静默；在病历生成中，Agent 必须守住边界，绝不能在对话未提及的情况下推断药物剂量或开具处方。

最后，审查者自身的专业资质是规格说明的一部分（Reviewer expertise is part of the specification）。普通全科医生与专科主任医生在判读复杂病例时的严谨度不同，评估器的置信度上限完全取决于标定它的专家级别。

### 2.1 缺陷模式解耦与专用评测器设计

针对上述特性，Abridge 放弃了使用单一综合评分（General Quality Score）来评判病历质量的通用做法。研发团队从线上反馈和临床事故案例中提取已知的失效模式，按发生频率与危害等级排序，归纳为准确性、合规性、风格规范与完整性四大维度，并为每种具体的失败模式构建独立的专用评测器。

例如，“症状归属错误”（将患者自我推测的病因写为医生的正式诊断）与“处方剂量幻觉”由完全不同的评测器承载。这种正交解耦确保了当测试失败时，工程团队能够精确锁定是事实一致性抽取存在缺陷，还是模板格式化提示词越界。

### 2.2 自动化提示词优化与双轨 Judge 架构

构建专用评测器最大的瓶颈在于对齐成本。早期做法是医生撰写标注指南，工程师反复手动修改评测 Prompt，比对双方打分直到接近。Abridge 将该流程升级为自动化提示词优化框架（Automated Prompt Optimization）：直接将临床指南与标注样本作为输入，由优化算法自动搜索并收敛出能够高保真对齐医生打分的 Judge Prompt。

在评测拓扑上，Abridge 采用了“无参考”与“基于参考”互补的双轨架构：

第一轨是无参考评测器（Reference-free judges）。该评测器不需要任何标准病历，直接将模型生成的病历与原始医患问诊语音转录本进行事实对照。由于脱离了对人工参考文本的依赖，无参考评测器不仅能在离线研发阶段运行，还能直接挂载到生产环境，对线上全量会话做持续实时监控。

第二轨是基于参考评测器（Reference-based judges）。该评测器将生成结果与经过专科委员会审核的典型案例进行深度比对。虽然维护专科金标案例的成本较高，但它能够捕捉特定专科领域内的术语习惯与推导深度，弥补无参考评测器在专科细微语境上的泛化粗糙度。

为了监控机器评测器本身的有效性，团队借助 LangSmith 的 Align Evaluator 工具持续比对 Judge 评分与临床医生的标注差异。更关键的工程细节在于：Abridge 要求标注医生在给出判决时必须提供文字解释（即使 AI 输出完全正确）。这些解释直接消除了标注过程中的主观噪声，为后续校准 Prompt 提供了可解释的调试线索。

## 3. 从单点打分到分阶段灰度发版门禁

拥有校准后的评测器后，如何将其嵌入交付流水线？静态单轮测试无法反映真实复杂系统的表现。例如 Included Health 的 Dot 助手基于 LangGraph 编排，用户最初可能只是询问某个核磁共振检查的报销比例，在长达数轮交互后，系统才逐步推导出该用户需要预约初级保健医生。

### 3.1 跨团队多轮会话仿真

在进行系统级底层重构时，回归验证是决定项目生死的核心。Included Health 曾将其导诊核心调度拓扑从旧版 Supergraph 全面迁移至 Deep Agents 架构。该变更横跨四个平行产品团队，系统行为稍有偏移就可能导致级联故障。

团队依靠既有的大规模多轮会话仿真套件，对历史各种边缘长尾对话流进行端到端重放。由于无需等待人工重新体验测试，团队在两周内完成了跨团队的核心架构迁移，且未引入任何重大质量回退。

### 3.2 观察隐式行为信号的五级渐进式发版

Abridge 将评估门禁串联成一套递进增强的发版流水线：

第一级：离线基准评测（Offline Evaluations）。每次代码提交与 Prompt 变更首先触发自动化基准集跑批，拦截基础功能缺陷。

第二级：历史病例回放测试（Backtesting against Historical Encounters）。将候选模型接入历史脱敏病例流，验证模型对真实语料变体的容忍度。

第三级：静默 A/B 灰度测试（Silent Rollout）。挑选 10% 到 15% 的合作机构流量接入新系统，但不强制更改医生交互。在此阶段，系统采集自动化评测无法感知的隐式行为数据——重点监控医生对生成病历的实际修改率（Edit Rate）、手动删除或补充词句的幅度，以及随后的定性打分。

第四级：全量受控发布（Full Release）。在灰度指标稳定且修改率低于基线阈值后，全量开放新版本。

第五级：生产全量监控（Continuous Production Monitoring）。线上实时运行轻量级无参考评测器，持续告警偏离分布的异常输出。

通过用历史数据与隐式行为替代纯人工阻断，Abridge 的系统发布周期从过去的一至两个月大幅削减至数天之内。

## 4. 生产可靠性的三维度量与资产回流机制

发版周期的缩短只有在生产质量稳定的前提下才有意义。Included Health 将线上可靠性拆解为三个不可替代的维度：

业务采纳度（Adoption）：会员是否愿意持续使用 AI 服务。Dot 上线后，平台对话互动量提升了 75%。

导诊决策质量（Routing Quality）：推荐的就医科室与层级是否恰当。在抽样审计中，临床医生对 Dot 转诊建议的认同度始终维持在 95% 的目标基线以上。

安全底线（Safety）：是否能准确识别急重症风险。审计显示系统在超过 99% 的高风险紧急医疗状况中正确触发了阻断与引导流程。

更重要的工程收获在于数据闭环。Included Health 将生产环境中的疑难会话分流至 LangSmith 标注队列（Annotation Queues），由临床专家进行二次判定。这一举措实现了“一次评审、三重复用”：

第一重：专家的裁决生成结构化标签，同步至企业数仓，形成实时运营监控大盘；
第二重：评审暴露的路由缺陷直接反哺给 Agent 技能定义（Skill Definitions），驱动 Prompt 与工具编排迭代；
第三重：该案例被收录为新的离线仿真回归用例，扩充自动化发版门禁的测试集。

## 5. 架构边界、合规代价与落地权衡

将专家评审基础设施化并非没有代价，工程团队在选型与落地时必须面对三项现实约束：

隐私数据治理（PHI Compliance）：评估链路必然捕获真实问诊轨迹、上下文状态与专家批注，这些数据均属于受保护的健康信息。Abridge 必须在数据流入评估流水线之前执行严格的去标识化处理（De-identification），并对评测系统设置细粒度审计与访问控制。依赖外部云端评估平台在合规上往往不可行，系统必须支持 VPC 私有化（Bring-Your-Own-Cloud）或完全自托管部署，这显著增加了评估集群的运维负担。

评测器自身的漂移（Evaluator Drift）：医学指南会更新，医保计费规则会调整，评测器并非一劳永逸。如果底层评估模型发生版本更迭，原先通过自动提示词优化得到的 Judge 可能会产生打分漂移。团队必须周期性抽样最新专家判定，对评测器本身执行反向校验。

专用评测器的推理成本与延迟：用多个针对单一故障模式的专用 Judge 替代单一 Judge，意味着离线评测与线上监控的推理 Token 消耗将呈倍数增长。在线上实时监控中，通常只能部署轻量级无参考规则，而将高开销的专科 Judge 限制在离线批处理或特定抽样队列中。

## 6. 面向高危业务 Agent 的工程落地评估清单

对于正在构建金融审查、法律分析或严肃企业流程 Agent 的工程团队，可参考如下落地自查清单：

维度一：资产化机制准备度
- 是否已建立结构化标注队列，而非依赖即时通讯工具传递缺陷？
- 是否要求业务专家在标注时给出判决理由与反思线索？
- 专家的判断是否能自动转化为结构化测试用例，而非仅沉淀为会议纪要？

维度二：评测器拓扑设计
- 是否已将质量评分拆解为具体正交的故障模式（如事实一致性、越权操作、拒绝回答时机）？
- 是否区分了通用的“无参考对照”与深度的“基于参考基准”？
- 是否建立了自动化的 Prompt 对齐机制，消除了人工反复猜测评测提示词的低效损耗？

维度三：交付流水线分级
- 是否存在多轮会话的离线仿真套件，用于保障核心框架重构的平滑性？
- 是否在真实上线前设计了低比例静默灰度，通过下游用户的“编辑率与修改轨迹”收集无偏信号？
- 紧急防御规则是否测试了“良性场景下的静默率”，避免过度警报打扰用户？

维度四：数据安全与闭环
- 评估流水线是否具备前置脱敏能力，杜绝生产敏感信息污染测试集？
- 生产环境捕获的失败样本能否在下一次发版前自动进入回归拦截集？

通过将稀缺的专家时间从“终审看门人”转换为“评估体系的设计者与校准者”，研发团队方能在不牺牲专业安全红线的前提下，将生成式 AI 系统的交付效率提升至现代云原生软件的标准节奏。
